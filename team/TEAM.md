# SCチーム（Samurai Chronicles 制作チーム）— 担当者制（2026-10-27〜）

主要な工程を**専任の担当者（サブエージェント）**に固定し、毎回同じ担当者を呼ぶ。担当者は自分のノートで
前回までの教訓と管理担当のフィードバックを引き継ぐ。毎月、管理担当がアナリティクスと作業記録から
各担当の貢献を評価し、フィードバックを返す。kagaku-life・lamp-whisper も同じ仕組み（各リポジトリの `team/TEAM.md`）。

## チームの目標

1. **視聴者の獲得** — 新しい視聴者に見つけてもらい、見てもらう
   - 指標: 公開後14日のインプレッション・CTR、非登録者の視聴（新規視聴者）、登録者の純増
2. **高評価の獲得** — 見た人に「良かった」と思ってもらう
   - 指標: 高評価数・高評価率（高評価 ÷ 再生）、非登録者の維持率・視聴秒、コメント数

SC本編（英語チャンネル）と SC学習版（英語で聴く日本史）は別チャンネルなので、目標の数値は別々に見る。

## 改善のサイクル（PDCA）

毎月、次の輪を1周させる。輪をつなぐのは「改善アクション」（管理担当が出す、担当ごとの具体的な行動。ID 付き、1人2件まで）。

| 段階 | 誰が | 何をする | 使うもの |
|---|---|---|---|
| Check（アナリティクス） | 管理担当 | 月次の `/sc-analytics` で数字を集め、前回までの改善アクションが効いたかを判定する | 集計、`team_stats.py`、`team_log.py summary`（適用した回・適用率） |
| 評価 | 管理担当 | 担当ごとに成果・品質・改善を採点する | `team_log.py score` |
| Act（フィードバック） | 管理担当 | 次に効きそうな行動を改善アクションとして登録し、ノートに書き出す | `team_log.py action add`、`sync-notebooks` |
| Do（行動の改善） | 各担当 | 作業の最初にノートの改善アクションを読んで必ず実行し、適用した回を記録する | `team_log.py applied`、担当メモ |
| （記録） | 進行担当（メイン） | 呼び出しの結果と、指摘の原文を記録する。自分の進行も記録し、評価を受ける | `team_log.py add`・`feedback` |

- **効果の判定は、適用した回の測定窓（公開後14日）がそろってから。** 制作から公開・測定まで時間がかかるので、
  あるアクションの判定は、出した月の翌月か翌々月の評価になることが多い。それまでは「判定待ち」で続ける
- 判定の結果: 効果あり → ノートの「続けている教訓」へ。2か月続けて効いたら CLAUDE.md・手順書への昇格を提案（ユーザーが承認）。
  効果なし・取り下げ → 閉じて、別のアクションを考える
- 月次評価を忘れないよう、制作コマンドの STEP 0 で `python3 team_log.py due` が前月の評価の有無を確かめる（済んでいなければ一言知らせる）

## 名簿

名簿の正本は `.claude/agents/*.md`（`python3 team_log.py roster` で一覧）。
**担当者は「SCチーム ○○担当 名前（カタカナ）」の形で呼ぶ**（例: 「SCチーム 脚本担当 クレア」）。会話・報告・評価・記録の表示はこの形にそろえる。
`Agent` の `subagent_type` と作業記録には呼び出し名（`sc-writer` など）を使う。`team_log.py` の `--agent` には名前（カタカナ）も書ける。

| チーム 担当 名前 | 呼び出し名 | モデル | 担当する工程 | 主に責任を持つ指標 |
|---|---|---|---|---|
| SCチーム 管理担当 マーカス | `sc-manager` | Opus | 月次のアナリティクスと評価・フィードバック（`/sc-analytics`・`/learn-analytics`）、チームの取りまとめ、エスカレーションの受け手（下記） | チーム全体の2目標 |
| SCチーム 進行担当 トーマス | `sc-coordinator`（メインの会話） | メイン（通常 Sonnet） | 制作コマンドの進行、担当者の呼び出し、担当のいない工程、記録（定義は `team/coordinator.md`） | 進行への指摘ゼロ・記録漏れゼロ・エスカレーションの遅れゼロ |
| SCチーム 企画担当 ヘンリー | `sc-planner` | Opus | `/sc-new` STEP 1 のトピック補充（人物・角度の提案） | 14日インプレッション・CTR・新規視聴者 |
| SCチーム 脚本担当 クレア | `sc-writer` | Sonnet | `/sc-new` STEP 2A のエピソードJSON（ナレーション・タイトル・画像プロンプト・説明欄） | 非登録者の維持率・高評価率・CTR（タイトル） |
| SCチーム 時代考証担当 エドワード | `sc-historian` | Opus | STEP 3A の制作確認書・ファクトチェック、STEP 5-0 の主人公の風体リサーチ | 史実・容姿の指摘ゼロ（ユーザー・視聴者） |
| SCチーム 映像担当 アイリス | `sc-art-director` | Opus | STEP 5C のクロスシーン一貫性チェック、画像のエスカレーション（WARNING が直らないシーン） | 画像の作り直し・画像の指摘ゼロ、維持率 |
| SCチーム 学習版台本担当 リリー | `sc-learn-writer` | Opus | `/sc-learn` STEP 1 の台本 | 学習版の維持率の曲線・高評価率 |
| SCチーム コミュニティ担当 ソフィー | `sc-community` | Sonnet | `/sc-upload` STEP 3.6・3.7 のコメント返信の文面 | コメント数・返信率・高評価率 |

担当のいない工程（サムネイル STEP 3B、BGM 選定 STEP 3C、TTS・動画生成などのスクリプト実行）は、SCチーム 進行担当 トーマス（メインの会話）が行う。
担当を新設・統合したいときは、管理担当が月次評価で提案し、ユーザーが決める。

## 呼び出しのルール

- 上の工程では、`Agent` の `subagent_type` に**担当名**を指定する（`general-purpose` を使わない）。`model` も担当の定義と同じ値を明示する
  （呼び出し側の `model` は担当の定義より優先されるので、違う値を書かない）
- 依頼文（プロンプト）には、これまでどおり手順書の指定どおりの内容を書く。担当者は会話の経緯を持たない
- 担当者は作業の最初に `team/notebooks/{担当名}.md` を読む（担当の定義に書いてある）。ノートは CLAUDE.md・手順書より下位で、
  食い違ったら CLAUDE.md・手順書に従い、食い違いを報告する
- 同じ工程を同じ回でやり直すときも、同じ担当を呼ぶ

## 記録（SCチーム 進行担当 トーマスが行う）

担当者の呼び出しが終わるたびに、結果を1行記録する。呼び出しの回数は SubagentStop フックが自動で記録するが（`.claude/settings.json`）、
結果（一発で通ったか・やり直したか）はメインにしか分からないので、手動の記録が評価の材料になる。

```bash
python3 team_log.py add --agent sc-writer --episode ep{NNN} --step 2A --result ok
#   --result: ok（一発で通った）/ retry（同じ担当にやり直させた）/ fail（失敗した）/ escalated（他の担当・管理担当に引き継いだ）
#   --retries N（やり直しの回数）、--note "短いメモ"
```

**成果物への指摘も記録する。** ユーザーの指摘・QA の不合格・視聴者のコメント（史実の誤りの指摘など）を受けたら、その成果物を作った担当に付ける。
指摘は原文のまま書く。

```bash
python3 team_log.py feedback --agent sc-historian --episode ep{NNN} --source user --severity major --text "指摘の原文"
#   --source: user / qa / viewer / manager、--severity: major（作り直しが要る）/ minor
```

**改善アクションの適用は、担当が自分で記録する**（`team_log.py applied`。担当の定義の手順3）。メインは、実施中の
アクションがあるのに担当メモに「適用した改善アクション」が無いときは、その場で担当に確かめる。

どの担当の成果物か迷ったら、その指摘を防げた最初の工程の担当に付ける（例: 容姿の誤り → SCチーム 時代考証担当 エドワード（`sc-historian`） の風体リサーチ、
シーン間の髪型の不一致 → SCチーム 映像担当 アイリス（`sc-art-director`））。担当のいない工程や、進行（呼び忘れ・手順の飛ばし・記録漏れ）への指摘は SCチーム 進行担当 トーマス（`sc-coordinator`）に付ける。

## エスカレーション

CLAUDE.md「モデルの使い分けとOpusへのエスカレーション」の条件に当たったときの引き継ぎ先:
- 画像（同じシーンが直らない・容姿の問題）→ SCチーム 映像担当 アイリス（`sc-art-director`）
- 史実・容姿の判断 → SCチーム 時代考証担当 エドワード（`sc-historian`）
- それ以外（スクリプトの失敗、原因の分からない不具合、担当をまたぐ問題）→ SCチーム 管理担当 マーカス（`sc-manager`）

引き継いだら、元の担当の記録を `--result escalated` にする。

## 月次評価（管理担当）

**毎月、前月分を評価する。第2月曜に `/sc-analytics`（SC本編の担当）、第4月曜に `/learn-analytics`（SC学習版の担当）。** 日程の正本は `team/schedule.json`。

材料:
- アナリティクスの集計（SC本編は `sc_yt_analyze.py --full`、SC学習版は `learning/learn_yt_analyze.py --json`）
- 高評価・コメント数（`/usr/bin/python3 team_stats.py --since {前月1日}`）
- 作業記録の集計（`python3 team_log.py summary --month YYYY-MM`）と、前月の評価・各担当のノート

評価の付け方（担当ごと）:

| 軸 | 見るもの | 点 |
|---|---|---|
| 成果 | 担当が責任を持つ指標（名簿の表）。同じ月の中央値・前月と比べる | 1〜5（データ不足なら `-`） |
| 品質 | 一発OK率、やり直し・引き継ぎの回数、指摘（重）の数 | 1〜5 |
| 改善 | 前月の改善アクションの適用率（機会のうち何回使ったか）と、その効果 | 1〜5（初回は `-`） |
| 総合 | 上の3つと、チームの目標への貢献 | S / A / B / C / D |

- **少ない本数の差を貢献と決めつけない。** 再生・高評価は企画・脚本・画像・公開時期の合作で、1つの担当に分けられない。
  `/sc-analytics` のしきい値（n<6 は測定不能 など）を守り、成果が判定できない月は `-` にして、品質と改善で評価する
- 評価は `team/evaluations/YYYY-MM.md` に書き、点は `python3 team_log.py score ...` で `team/scorecards.jsonl` に残す
- 前回までの改善アクションを判定して閉じ（`team_log.py action close`）、新しい改善アクションを登録して（`action add`）、`sync-notebooks` でノートに書き出す
- 各担当のノートの「管理担当からのフィードバック」を書き換える（行動に落とせない所感。具体的な回と箇所を挙げる）
- **管理担当が自分で変えてよいのはノートと評価の記録だけ。** CLAUDE.md・手順書・担当の定義（`.claude/agents/`）の変更は提案にとどめ、
  ユーザーの承認を取ってから反映する（`/sc-analytics` STEP 5〜6）
- 総合 D が2か月続いた担当は、担当の定義・依頼文・モデルの見直し案を出す

## ノート（`team/notebooks/{担当名}.md`）

担当者の引き継ぎノート。担当者が作業の最初に読む。

- 「改善アクション（実施中）」: `team_log.py sync-notebooks` が書く（手で直さない。正本は `team/actions.jsonl`）
- 「管理担当からのフィードバック」: 管理担当が毎月書き換える
- 「続けている教訓」: 管理担当が、繰り返し効いている教訓だけを残す（ルールとして確定したものは CLAUDE.md・手順書に移して、ここから消す）
- **80行以内**（毎回読ませるため。超えたら管理担当が削る）
- 担当者は作業中にノートを書き換えない。気づいたことは報告に書き、メインが `team_log.py add --note` か `feedback` で残す
